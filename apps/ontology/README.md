# SenClaw Ontology

Turn raw data into a real **RDF knowledge graph** — the right way. A self-contained
SenClaw Space App: Rust + [axum] backend embedding an [Oxigraph] triple store (SPARQL 1.1),
a React explorer, an `ontology-mcp` server, two skills, and a persona.

It follows the discipline that separates a real ontology from "a database schema in RDF
clothing": **the T-Box (schema) is designed from competency questions; the A-Box (data) is
generated by a declarative mapping** and re-run whenever sources change.

## The short version — the Studio tab

Drop a file, press one button, ask a question.

1. **Drop any file.** Format detection is by magic bytes and structure, never the
   extension: CSV/TSV/PSV (delimiter auto-sniffed) · Excel `.xlsx/.xlsm/.xls/.ods` (one
   source per sheet, dates decoded) · JSON — nested, wrapped (`{data:[…]}`) or JSON Lines ·
   YAML · XML (attributes become `@name` columns) · Markdown & HTML tables · Word `.docx` ·
   PDF text layer · plain prose. Nested structures are flattened to dotted paths
   (`customer.name`, `items.0.sku`) because **a value the mapping DSL cannot name is a
   value the ontology can never reach**. Prose becomes a `text` source for AI extraction.
2. **✨ Auto-build.** One background job runs the entire discipline — profile → draft
   competency questions → design the T-Box → author the mapping → *mechanically repair it*
   → lift → extract from documents → draft SHACL shapes → validate → write SPARQL for each
   competency question and run the suite → materialize inferences. Live per-step progress;
   every stage stays editable in the numbered tabs afterwards.
3. **💬 Ask.** A question in plain language comes back as a sentence — with the SPARQL it
   ran and the rows it read, so the answer is always checkable rather than merely
   plausible.

**The AI only ever drafts; the deterministic pipeline decides.** Every drafted mapping is
checked against the real column names before it can run: a predicate-object map naming a
column that does not exist is dropped, an unresolvable subject template falls back to a
stable hash of the identifying columns, a hallucinated source name is re-pointed, and a
triples map with nothing usable left is discarded. The repairs are reported, not hidden —
a bad triple is worse than a missing one. NL→SPARQL is likewise grounded on the *live*
schema (classes and predicates that actually occur, with counts), not only on the declared
T-Box, which is what stops confidently-empty answers.

## AIP Assist — context-aware RAG over metadata

A sidebar you can open from **any** tab (`◆ Assist`). The same question gets a different
answer depending on where you are standing.

```text
   question ──┐
              ├──► retrieve  ──► top-k chunks ──► LLM ──► answer + numbered citations
   session ───┘   (BM25 over        ▲                        (each citation jumps to
   context         the metadata     │                         the tab it came from)
   · tab           index)           │
   · open source ──────────────────-┘  re-ranks: your tab, the source you have open
```

**It indexes metadata, never data.** Source and column names with their profiled types and
roles, class and property IRIs, the mapping's structure, SHACL constraints, competency
questions, lineage batches, activity logs, and the app's own documentation — and
deliberately *no* cell values, samples or literals.

That boundary is the point, not a limitation. A sidebar open on every screen has no
per-row access control in front of it, so anything in the index is effectively visible to
anyone who can open it. Keeping values out is what makes it safe to leave open, so it is
enforced in `redact()` plus value-free builders and guarded by a test that lifts a
distinctive literal into a project and asserts it appears in no document — rather than
merely requested in a prompt.

When you ask something that genuinely needs values (*"how many products?"*), Assist says
so and hands off to **Ask the graph** / SPARQL, which do read the data. It does not
assemble a number out of schema names that happen to contain the right nouns.

Retrieval details worth knowing (each earned by a failing test):

- **Aboutness is identity, not word overlap.** Opening the `suppliers` source must not
  boost a different source that merely *has* a `supplier` column, so the context match is
  against a declared subject, never body text.
- **Tab boost is tapered by how many tabs a chunk claims.** A chunk specific to one stage
  earns the full boost; one that declares itself relevant everywhere earns almost none —
  otherwise a catch-all doc wins on every tab and the context stops discriminating.
- **Function words are filtered before ranking.** Six near-zero contributions from
  "what / does / this / with / and / do" otherwise outweigh one real term and hand every
  question to whichever chunk is chattiest.
- **Light stemming and Vietnamese diacritic folding**, so *validate* reaches *validation*
  and `san pham` reaches `sản phẩm`.
- **Context fallback.** "What does this do?" carries no lexical signal, yet it is the most
  natural thing to type into a sidebar — so a question that retrieves little is topped up
  from the current tab, most specific chunk first.

`GET /api/projects/:id/assist/index` returns the whole index, so the metadata-only claim
is inspectable instead of something you have to take on trust.

## AIP Logic — the LLM writes *proposals*, not data

The Logic tab is where "LLM intuition" meets "data truth". An LLM never writes SPARQL here.
It emits a small **typed action** — `add_individual`, `set_attribute`, `add_relation`,
`link_entities` — and each action is **validated against the T-Box before it can become a
triple**: a hallucinated class or a data property used where an object property belongs is
rejected *at proposal time*, not discovered later as a broken edge. This is the "typed IR,
not free code — the type checker blocks the LLM" principle.

A **Logic function** applies a plain-language instruction to your data:

- **extract** pulls facts out of a text source ("extract the companies and the supply
  relationship between them").
- **classify** is the run-time LLM node: it runs the instruction over **each row** of a
  source at scale (with per-row retry for rate limits, and a **trial run** to preview on a
  few rows first), enriching the entity the lift already minted — not an orphan node.
- **resolve** finds duplicate individuals of a class by Jaro-Winkler label similarity
  (**no LLM** — deterministic) and proposes `skos:closeMatch` links. Entity resolution goes
  through the *same* review-then-apply queue as everything else, rather than a side channel.

Whatever a function produces lands in the **proposal queue**, never in the graph. A human
reviews each typed action (with its rationale and confidence) and approves or rejects;
approval re-validates against the current T-Box and applies the survivors as **one
provenance batch you can drop**. Human-in-the-loop is the default; `autoApply` is an
explicit opt-in and is still fully audited. Approvals are **reversible**: dropping a logic
batch (on the Reason & Provenance tab) removes its triples *and* reverts the proposals that
fed it back to pending, so the audit trail never claims a proposal is "approved" after its
data is gone. This is the "writes are proposals, every
mutation carries validation + audit" principle.

**Evals from day one**: save `input → expected` cases for a function and run them across one
or more SenClaw models — the harness runs each case twice to surface run-to-run variance and
reports a pass rate, so you can compare models before trusting one. (In testing it caught a
real miss where a model failed to classify "máy giặt" as an appliance — which is the point.)

The five principles this app now embodies: **the ontology is the shared contract** (pipeline,
Ask, Assist and Logic all speak the same classes); **the LLM generates typed IR, not free
code**; **metadata for the LLM, data for the engine** (Assist sees schema, never values);
**writes are proposals** through validated, audited Actions; **evals from day one**.

## The pipeline (mirrors the app's tabs)

| # | Stage | What it does |
|---|---|---|
| 0 | **Studio** | Drop any file · one-click Auto-build with live progress · Ask in plain language. |
| ◆ | **Assist** | Context-aware RAG sidebar over project metadata + platform docs, from any tab. |
| 8 | **Logic** | LLM functions that propose **typed actions** on the ontology, reviewed in a human-in-the-loop queue. |
| 1 | **Sources** | Upload/paste a source; every column is profiled (type, null ratio, uniqueness, enum, heuristic role). ✨ AI can refine the roles. |
| 2 | **Ontology (T-Box)** | Design classes & properties by hand or ✨ draft them from your competency questions. Enum→SKOS individuals, attributed relations→reification. |
| 3 | **Mapping** | A declarative **RML-lite** JSON DSL (mapping is *data, not code*): templated & hashed IRIs, typed literals, entity joins. Preview, then lift. |
| 4 | **Explore** | SPARQL console (prefixes auto-declared, union-of-all-graphs default), ✨ NL→SPARQL, and a live graph view. |
| 5 | **Competency** | Save competency questions + the SPARQL that answers each, and run them as a **pass/fail test suite** — the ontology's acceptance test. |
| 6 | **Validate** | **SHACL-lite** (closed-world): cardinality, datatype, class, nodeKind, numeric range, regex. ✨ draft shapes from the T-Box. |
| 7 | **Reason & Provenance** | RDFS/OWL-RL materialization (open-world) · per-import **provenance batches** you can drop/reload · Jaro-Winkler **entity resolution** · LLM **extraction from text**. |

## Design decisions

- **Oxigraph, in-memory** (no RocksDB C++ build), persisted per project as a TriG snapshot
  in a small rusqlite metadata DB. Named graphs give provenance; a store-wide *partition
  invariant* (each triple lives in exactly one graph) keeps the union-default query graph a
  proper set.
- **Custom RML-lite mapping DSL** rather than a full RML engine — there is no mature
  pure-Rust RML engine, and a compact interpreted DSL keeps the mapping declarative and
  auditable while the app stays a single self-contained binary.
- **In-house SHACL-lite over SPARQL** rather than the rudof crate — avoids the
  oxrdf-version alignment risk and keeps everything in one binary.
- **LLM via the SenClaw bridge only** — the app never sees provider keys. It runs on the
  daemon's active model by default; the **◆ AI model** picker in the sidebar footer (fed by
  `GET /api/models` → the daemon's `/api/llm-config`) pins the ontology work to a specific
  configured model **without changing the model everything else shares** — the same per-app
  `llm_profile` pattern as moltbook / rewrite-story. The choice is persisted in the app's
  `settings` table and re-applied on restart; `ONTOLOGY_LLM_PROFILE` only seeds it on first
  run. Picking here never calls the daemon's *set-active-model* — that would hijack every other
  app and the agent. **Reasoning models** (deepseek-*-flash, o-series, etc.) spend the
  token budget on a hidden trace *before* emitting a visible character, so JSON drafts come
  back chopped mid-string on a budget that is generous for a plain chat model — the app sizes
  budgets ×4 for this and, when the bridge reports `finish: "length"`, says *"hit the token
  limit"* rather than the misleading *"did not return valid JSON"*. Runtime-verified end to
  end on `deepseek-v4-flash`.
- **Normalize at ingest, not downstream.** The sniffer converts every format into exactly
  one of two shapes (a flat table, or text), so `profile` / `mapping` / `lift` never had to
  learn about spreadsheets or XML — they still only ever see a `Table`.
- **Documents are chunked before extraction.** The bridge returns a roughly fixed amount of
  output regardless of input size, so a whole report in one prompt comes back *summarized*
  — i.e. most facts silently dropped. Chunking on paragraph boundaries (char-based, so
  Vietnamese can never be cut mid-codepoint) is what makes long-document extraction real.
- **Autobuild is a background job**, polled by id — a full build is a dozen bridge
  round-trips, far past any HTTP timeout.

## Develop

```bash
# backend (from repo root)
cargo run -p ontology            # serves http://localhost:4410
cargo test -p ontology

# web UI
cd apps/ontology/web && npm install && npm run dev   # proxies /api to :4410
```

## Package

```bash
apps/ontology/scripts/pack.sh    # → apps/ontology/ontology-app.zip
```

Installs into SenClaw as a Space App: `runtime.start = ./ontology`, MCP `ontology-mcp`
auto-registered, skills `ontology-build` / `ontology-query`, persona `ontology-engineer`.

## MCP tools (`ontology-mcp`)

The easy path: **`ontology_ingest`** (any format, auto-detected) → **`ontology_autobuild`**
(+ `ontology_autobuild_status`) → **`ontology_ask`**.

**`ontology_assist`** is the same context-aware metadata RAG the sidebar uses — pass the
tab the user is looking at and the source they have open, and an agent gets answers about
*how the platform works* and *what is defined in this project*, with citations. It cannot
read data; `ontology_ask` is for that.

**AIP Logic** (typed actions as reviewable proposals): `ontology_create_function` ·
`ontology_list_functions` · `ontology_trial_function` · `ontology_run_function` ·
`ontology_list_proposals` · `ontology_approve_proposals` · `ontology_reject_proposals`.

Everything else, for manual control: `ontology_list_projects` · `ontology_create_project` ·
`ontology_add_source` · `ontology_get_tbox` · `ontology_live_schema` ·
`ontology_add_class` · `ontology_add_property` · `ontology_apply_tbox` ·
`ontology_set_mapping` · `ontology_preview_mapping` · `ontology_lift` ·
`ontology_sparql` · `ontology_add_competency` · `ontology_run_competency` ·
`ontology_set_shapes` · `ontology_validate` · `ontology_materialize` ·
`ontology_resolve_candidates` · `ontology_list_batches` · `ontology_drop_batch` ·
`ontology_extract`
